# Postmortem 验尸报告

`postmortem/` 目录记录项目历史上的严重缺陷复盘。每篇 PM 包含根因分析、反模式标识和预防措施。

本技能覆盖两个独立场景，根据上下文判断进入哪个流程：

- **场景 A：编写新 PM** — 刚修复完一个 bug，需要复盘记录
- **场景 B：回归检查** — 开发新功能或准备提交代码，对照已有 PM 排查风险

---

## 场景 A：编写新 PM 报告

**触发时机**：修复了一个 bug（尤其是被 revert、反复修复、或线上事故的），需要复盘。

```
编写进度：
- [ ] A1：分析本次修复的 bug
- [ ] A2：确定编号和严重级别
- [ ] A3：撰写 PM 报告
- [ ] A4：更新索引
```

### A1：分析本次修复的 bug

收集信息：
- 查看问题修复相关的 commit 历史
- 确认 bug 的现象、影响范围、根本原因
- 找出引起问题的原始 commit 和修复 commit

### A2：确定编号和严重级别

读取 [postmortem/INDEX.md](../../../postmortem/INDEX.md) 获取当前最大编号，新编号 = 最大编号 + 1。

严重级别定义：
- **P0-紧急**：线上服务不可用，影响所有用户
- **P1-高**：核心功能不可用，或内存泄露/进程无法退出
- **P2-中**：功能异常但有 workaround，影响范围有限
- **P3-低**：边缘场景问题，影响极小

### A3：撰写 PM 报告

在 `postmortem/` 下创建 `PM-XXX-<简短标识>.md`，使用以下模板：

```markdown
# PM-XXX: <简短标题>

## 基本信息
- **严重级别**: P0-紧急 | P1-高 | P2-中 | P3-低
- **影响模块**: `packages/<name>/src/<path>`
- **影响范围**: <谁受影响>
- **时间线**: <关键时间节点>

## 事故描述
<现象，1-3 段>

## 引起事故的 Commits
| Commit | 日期 | 描述 |
|--------|------|------|

## 修复的 Commits
| Commit | 日期 | 描述 |
|--------|------|------|

## 根因分析
<附代码示例，标注 ❌ 错误写法和 ✅ 正确写法>

## 经验教训
1. <教训>

## 预防措施
- [ ] <可执行的检查项>

## 模式识别
**反模式**：<一句话概括，用于快速匹配>
```

编写要求：
- 「模式识别」是最关键的章节，必须提炼为可快速匹配的一句话反模式描述
- 「根因分析」必须包含 ❌/✅ 代码对比
- 「预防措施」必须是可执行的 checklist，不是空话

### A4：更新索引

在 `postmortem/INDEX.md` 的表格末尾追加一行，格式与现有行一致。

---

## 场景 B：回归检查

**触发时机**：完成功能开发、准备提交代码时。

```
检查进度：
- [ ] B1：收集本次变更信息
- [ ] B2：读取索引，筛选相关 PM
- [ ] B3：逐条比对反模式
- [ ] B4：输出检查报告
```

### B1：收集本次变更信息

运行 `git diff --name-only` 和 `git diff --cached --name-only` 获取变更文件列表，确定涉及的模块和改动类型。

### B2：读取索引，筛选相关 PM

读取 [postmortem/INDEX.md](../../../postmortem/INDEX.md)，根据变更涉及的模块匹配相关 PM。

### B3：逐条比对反模式

读取每篇相关 PM 的「**模式识别**」章节，对照本次代码变更逐条检查是否命中。

### B4：输出检查报告

```markdown
## Postmortem 回归检查报告

**变更模块**: <涉及的模块>
**检查的 PM**: <PM 编号列表>

### 命中的反模式
- PM-XXX: <反模式描述> → <文件:行号> → <修复建议>

### 检查通过
所有已知反模式均未触发。
```

命中任何反模式 → **必须修复后才能提交**。
