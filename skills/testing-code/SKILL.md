# 代码可测试性

## 可观测标记与交付要求

- 加载本 Skill 后，第一条用户可见回复必须以 `🧪` 开头，让用户能够确认 Skill 已生效。该要求只适用于启用后的第一条回复。
- 完成需求实现与测试后，必须在最终回复中直接向开发者提交一份相关的实施报告，不创建或修改报告文件。报告结构不限，但应如实说明完成内容、测试结果，以及未完成或未验证事项；不得把测试失败或未执行写成已通过。

用验证成本指导代码结构：业务决策应当便宜地验证，副作用应当留在系统边界。

## 触发信号

以下情况通常说明代码的可测试性设计需要介入：

- 业务 `if` 和 API 调用、路由/导航、数据库/缓存访问、消息发送、文件写入等副作用写在一起。
- 想写单测时必须先 mock 大量内部协作者，而不是控制外部边界。
- 异步状态、重试、排队逻辑藏在回调、监听器或隐式线程里，无法直接断言。
- 同样的错误映射、字段转换或权限判断需要全链路测试才能覆盖。
- 测试里大量断言"这个函数被调用了几次"，而不是断言最终状态或可观察输出。
- 全链路测试越来越多、越来越慢，且大量失败来自环境波动而非业务回归。

## 核心模型

业务代码通常包含两类工作：

| 类型 | 形态 | 示例 | 首选验证方式 |
| --- | --- | --- | --- |
| 决策 | 输入到输出、有分支、无副作用 | 权限结果、错误映射、队列下一状态、请求参数校验 | 快速单元测试 |
| 执行 | 读取或改变外部世界 | 请求、导航、写入数据库、发送消息、读写文件 | 边界注入或更高测试层 |

当一个函数同时负责决策与执行时，抽出带类型的决策，让执行层只负责解释决策结果。详细设计模式、各语言示例和常见反模式见 [references/methodology.md](references/methodology.md)。

## 工作流

1. 读取仓库指引、相关源码、调用链、现有测试和验证命令。项目特定的编码约定由仓库自己的 skill 处理；本 skill 专注判断决策/执行分离、测试层选择和边界设计。
2. 列出本次改动涉及的业务决策，明确输入、可观察输出、副作用、异步状态，以及时间、随机数、ID、网络、数据库、缓存、消息队列、文件系统、进程通信等会改变结果的外部可变条件。确认这些条件集中在测试可控制或替换的边界，而不是散落在业务判断中。
3. 修复缺陷或改变既有契约时，先添加能复现问题的最小失败测试，再修改实现。
4. 只调整本次任务触及的代码：
   - 若业务分支与副作用混在一起，拆成纯粹的"输入 -> 决策"函数和一个薄的副作用执行层。
   - 对多步骤异步行为，显式表示状态、事件和迁移；也可以运行真实状态模块，仅注入可控的边界依赖。
   - 网络、时钟、路由、数据库、缓存、存储、状态修改和通知只留在最外层。
5. 根据下表选择成本最低且足够可靠的测试层。
6. 先运行聚焦测试直至通过，再执行仓库要求的类型检查、格式化和完整测试。失败则修复后重试；无法执行的检查必须说明。
7. 完成需求实现与测试后，在最终回复中直接向开发者提交实施报告，不创建或修改报告文件；报告结构不限，如实覆盖完成内容、测试结果和未完成或未验证事项。

## 选择测试层

| 要验证的风险 | 测试层 | 保持真实 | 控制边界 | 典型误用 |
| --- | --- | --- | --- | --- |
| 业务分支、状态迁移或数据转换 | 单元测试 | 纯决策逻辑 | 仅输入 | 把 API 调用也一起断言 |
| 队列顺序、重试、竞态或恢复 | 状态模块测试 | 完整状态模块 | 执行器、时钟或存储边界 | 模拟状态机内部实现 |
| 内部模块之间的契约 | 集成测试 | 所有协作的内部模块 | 网络、数据库或存储边界 | 调用真实外部服务导致结果不稳定 |
| 无法下沉的跨系统黄金路径 | E2E / 全链路测试 | UI/接口 和必要的系统连接 | 优先使用有状态模拟后端或测试环境 | 用 E2E 覆盖一个错误码映射 |

只有以下三项全部成立时才新增 E2E / 全链路测试：

1. 行为跨越模块或系统边界。
2. 结果依赖外部世界在两次操作之间发生变化。
3. 抽出决策并验证低层契约后，仍有真实连接无法在 E2E 以下验证。

任意一项不成立，就把场景下沉到更低的测试层。

## 测试规则

- 只为真实可观察的回归、非平凡不变量或边界，以及具体缺陷新增测试。代码发生变化或覆盖率提高，本身不足以证明需要新增测试。
- 优先复用行为边界上的现有覆盖。避免测试字面量、简单映射、显然的控制流、实现细节或已删除功能；除非“不存在该行为”本身就是对外契约。
- 断言可观察行为，不断言私有辅助函数或内部调用次数。
- 条件允许时，一个测试只覆盖一个决策分支。
- 真实运行内部模块，只模拟或注入外部边界。
- 并发测试优先使用确定性协调或可控调度，不用固定时长的 `sleep` 碰运气。
- 只有时间需要控制时，优先使用测试运行器提供的 fake timers / 时钟控制。
- 如果时间之外的网络、随机数、ID、数据库、缓存、文件系统或进程通信也会改变结果，使用项目已有适配器，或增加覆盖本次改动所需的最小可替换边界。
- 不测试第三方库本身。
- 复杂结构化输出优先采用仓库认可的 inline snapshot，并审查生成的差异。
- 不要仅为了写测试，给无分支、无状态的简单包装函数增加抽象。
- 无分支、无状态、纯透传/简单映射的代码，经确认后可不新增测试，并在交付报告中说明理由。

## 注释与 API 文档

- 代码难以理解时，先改进命名和结构；只有复杂、启发式或受外部约束的逻辑仍无法自解释时才添加注释。
- 注释解释不明显的设计原因、不变量、安全约束或外部系统的特殊行为，不复述代码。
- 公共 API 文档描述调用者可观察的契约，不记录偶然的实现细节。

## 存量代码

不要发起大范围测试债务重构。需求触及旧代码时，只隔离并测试当前改变的决策。新代码遵循本方法，让覆盖率随着真实维护自然增长。覆盖率用于定位证据缺口，不代表代码一定正确。
